Important Rules

  • One signature works everywhere: The recommended, unified signature runs in all three modes — 1v1, N-Player, and OS Simulation. If your strategy is named "myStrategy", write:
    def myStrategy(last_moves, my_history, opponents_histories, meta):
    • last_moves — list of each opponent's last move (in 1v1 / OS sim this is a single-element list; empty on the first round).
    • my_history — your own past moves; opponents_histories — a list of per-opponent move histories.
    • meta['round'] — current round number (starts at 0).
    • meta['rng'] — a seeded random generator; use meta['rng'].random() or meta['rng'].randint(0, 1) so runs stay reproducible (preferred over the bare randint).
    • meta['tournament_info'] — context dict (ranking weights, active modes, n_players); meta['player_index'] and meta['n_players'] — your seat and the group size.
  • Function Name Must Match Strategy Name: the function name must equal the strategy name you enter.
  • Return Only 'C' or 'D': Return exactly 'C' to cooperate (yield the CPU) or 'D' to defect (keep running). Any other value fails the strategy.
  • Handle the first round: on the first round last_moves is an empty list (no history yet).
  • Legacy 3-arg form still accepted: the older def myStrategy(opponent_last_move, my_history, opponent_history) still works (it sees all opponents as one aggregated opponent; opponent_last_move is None on the first round). A separate myStrategy_nplayer companion is no longer required, though it is still honoured if present.
  • Perfect Python Syntax Required: Any syntax error causes your strategy to fail completely.
  • Random choices: a bare randint(0, 1) is available in every mode, but prefer meta['rng'].randint(0, 1) / meta['rng'].random() so seeded runs stay reproducible.
  • Whitelisted libraries: you may import only these standard modules (same in all three modes): math, random, collections, itertools, functools, statistics, heapq, bisect, copy, operator, fractions, decimal, enum, typing, dataclasses, string, re, abc, contextlib, numbers. Anything else (e.g. os, sys, socket, file/network access) is blocked, and only a restricted set of builtins is available (abs, all, any, bin, bool, bytes, callable, chr, classmethod, complex, dict, divmod, enumerate, filter, float, format, frozenset, hash, hex, id, int, isinstance, issubclass, iter, len, list, map, max, min, next, object, oct, ord, pow, property, range, repr, reversed, round, set, slice, sorted, staticmethod, str, sum, super, tuple, type, zip).
  • Classes and exception handling work: you may define classes inside or alongside your strategy, and try/except is supported for the standard exception types (Exception, ValueError, TypeError, KeyError, IndexError, LookupError, AttributeError, NameError, ZeroDivisionError, ArithmeticError, OverflowError, FloatingPointError, RuntimeError, RecursionError, StopIteration, NotImplementedError, AssertionError). Note that except Exception will not catch the instruction-limit abort, so it cannot be used to hide an infinite loop.
  • Attribute access: getattr, setattr, hasattr and delattr are available but cannot reach names beginning with an underscore — the same rule that blocks writing x.__class__ directly. Storing state on your own function (e.g. MyStrategy.counter = 0) is fine.
  • Per-round work limit: each call to your strategy may execute up to 200,000 Python line-steps. That is generous enough for history-scanning and model-building strategies, but an infinite loop is aborted and the match ends.
  • OS Simulation specifics: there is no cap on strategies (it runs on your own machine, so you get a time estimate before a big run instead). Cores must be 2–8. Homogeneous benchmarks each strategy across all cores; Heterogeneous evaluates every combination of your strategies across the cores, so it needs at least as many strategies as cores. A heterogeneous run is time-boxed to 5 minutes and reports a random sample of the combinations if it runs out; tick Remove limits to sweep all of them.
  • Strategy Names Must Be Unique: Each strategy must have a different name.
Example (Tit-for-Tat, works in every mode):
def TitForTat(last_moves, my_history, opponents_histories, meta):
    return last_moves[0] if last_moves else 'C'

OS Simulation

Benchmark your strategies as CPU-core scheduling personalities. Each submitted strategy runs on the cores (homogeneous: one strategy across all cores; heterogeneous: every combination of strategies across the cores); the chosen scheduler interprets each Cooperate (yield) / Defect (keep running) move natively. See How it works — modes & scoring above for details.

Sizing an OS Simulation run

This all runs on your own machine, so the only budget is your CPU and your patience. There is no cap on the number of strategies, and 1v1 and N-Player matches are milliseconds. Cost here comes almost entirely from how you set Core Assignment below.

Homogeneous — cheap, scales linearly

Each strategy is benchmarked across all cores: cost grows with the number of strategies (one run each), not combinatorially. Safe for any reasonable count.

Heterogeneous — combinatorial, so it is time-boxed

Every way of dealing your strategies onto the cores is evaluated, one distinct strategy per core: that is C(strategies, cores) runs, each over the 4 workload profiles (Uniform, Poisson, Mixed, Bursty). One combination costs roughly 0.4 seconds, near enough independent of the core count, so the combination count is the cost:

What happens when a run is large

A run is never refused for being expensive. Heterogeneous gets a 5 minute budget; it times each combination as it goes and stops once the next one would overrun. You are told the projected cost before anything starts, and whatever it did not reach is simply not evaluated: the results say "750 of 3003 (sampled)" and show a banner, rather than a number that looks complete.

The combinations that do run are picked at random (seeded off the run's seed, so a run is still reproducible), never as the first N in order. That matters: C(n,k) enumerates low indices first, so taking a prefix would let a strategy's rank depend on where it sat in your list. Picking at random gives every strategy roughly equal exposure.

The trade: a sampled ranking is a good estimate, not a proof. The top mixture is the best of those evaluated; an unevaluated one may beat it. When you need the definitive answer, tick Remove limits below to sweep the whole space, and be ready to wait for it.

Rules of thumb

  • Cores must be between 2 and 8.
  • Heterogeneous needs at least cores strategies, since each core gets a different one. This is the one thing still refused outright, because fewer strategies than cores cannot be arranged at all.
  • C(n,k) is symmetric and peaks when cores ≈ strategies/2, then falls again — so moving the core count away from the middle in either direction (fewer or more cores) makes a run cheaper. At the extreme, cores = strategies gives exactly one layout.
  • To cover the whole space without a long wait, nudge cores away from strategies/2 or use fewer strategies, rather than removing limits.
What do these terms mean?
Homogeneous
Every core runs the same strategy. Each strategy is tested on its own, then they are compared.
Heterogeneous
Each core runs a different strategy (each used at most once). Every mixture is tried and ranked, to find the best team.
Cooperate / Defect here
Cooperate = be nice and give up the CPU; Defect = grab the CPU and hold it. Each scheduler below turns that into its own action.
FCFS (First Come, First Served)
Jobs run in arrival order until they finish. Strategies have no effect, so it is a plain baseline.
Round Robin
Jobs take turns in time slices. Cooperate = short slice (yield early); Defect = long slice.
SJF / SRTF (Shortest Job First / Shortest Remaining Time First)
Shortest job runs first. Cooperate follows that rule; Defect grabs the longest job and holds it.
Priority
Cooperate = low priority, short slice; Defect = top priority, runs to completion.
MLFQ (Multi-Level Feedback Queue)
Several queues from high to low priority. A core that yields early (Cooperate) stays high; one that uses its whole slice (Defect) moves down.
CFS (Completely Fair Scheduler, as in Linux)
Shares CPU time by weight. Cooperate = low weight (takes less); Defect = high weight (takes more).
Affinity-aware
Each core keeps its own queue so caches stay warm. Idle cores take work from busy ones, but a Defecting core refuses to give its work away.
Baseline
The chosen scheduler with no strategy at all, shown as a grey reference row and bar.
